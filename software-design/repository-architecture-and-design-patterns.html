Repository Architecture & Design Patterns

Why debates between Monorepos, Modular Monoliths, Hexagonal Architecture, Vertical Slices, and DDD talk past each other—and how to choose deliberately across all four architectural scales.

Engineering teams routinely treat architectural styles as mutually exclusive binaries. In reality, repository topology, module boundaries, dependency direction, and internal domain modeling govern four distinct scales of a codebase. A single monorepo can house a modular monolith where one complex billing module uses Hexagonal Architecture and DDD Aggregates, a configuration module uses Transaction Scripts, and a reporting endpoint queries flat SQL read models.

02 · Empirical Evidence Production Migrations · Failure Modes · Dual-Write Reliability

When Boundaries Fail—and How Real Teams Recovered

Shopify avoided a distributed monolith by fixing internal boundaries inside one deployable unit. Meanwhile, Carrier, Appsmith, and Gusto illustrate when modularity beats premature service extraction.

Primary Case Study

Shopify’s Componentization: 2.8M Lines Without Microservices

Ruby on Rails · 1,000+ Developers · 500,000 Commits

Before 2017, Shopify’s Rails monolith grouped files by technical role (models/, views/, controllers/). Shipping-rate logic called directly into tax-rate code, triggering cascade test failures. Yet Shopify ruled out a blanket microservices rewrite: everything engineers liked about velocity came from living in one codebase; everything they hated came from missing boundaries.

PHASE 01 · 2016

Crossing the Design Payoff Line

Referenced Martin Fowler’s Design Stamina Hypothesis: onboarding engineers on Shipping had to learn Orders and Payments just to ship one feature.

PHASE 02 · 2017

6,000-Class Domain Reorg

Mapped ~6,000 Ruby classes in a spreadsheet to domains (orders, shipping, inventory, billing) and moved them in one automated PR (requiring git --follow for history).

PHASE 03 · ENFORCEMENT

Wedge & Packwerk

Built Wedge (CI Ruby tracepoints detecting cross-component calls & ActiveRecord associations) and Packwerk + Rails Engines to enforce public module APIs.

PHASE 04 · PAYOFF

Surgical Swaps & Selective Split

Swapped out the legacy tax engine cleanly. Extracted only high-throughput Storefront Rendering and sensitive Credit Card Vaulting into separate services.

On-Premises Single Binary

Appsmith

Rejected microservices because end-users deploy Appsmith on-premises. A modular monolith preserved clear internal boundaries while shipping as a single binary without distributed deployment overhead.

Strict API Boundary

Gusto (Time Tracking)

Built Time Tracking as a module inside a modular monolith with explicit API contracts that forbid passing rich objects across boundaries—avoiding costly rework if initial service boundaries were wrong.

Composable Commerce

Carrier HVAC & Tony’s Chocolonely

Carrier cut site launch cost from ~$2M / 12 months on a traditional monolith to ~$100k / 30 days (~10% cost) using modular components (OneCommerce). Tony’s Chocolonely gained 2.5× faster site speed unifying DTC, B2B, and resellers.
