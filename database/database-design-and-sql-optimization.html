Invariant · Fact Ownership

Current Facts vs. Historical Snapshots

Storing unit_price_at_sale on order_items while products.list_price remains mutable is not denormalization. They are two distinct real-world facts. 

CREATE TABLE products (
  product_id   VARCHAR(10) PRIMARY KEY,
  product_name VARCHAR(100) NOT NULL,
  list_price   NUMERIC(10,2) NOT NULL -- today's catalogue price
);

CREATE TABLE order_items (
  order_id           INT REFERENCES orders(order_id),
  product_id         VARCHAR(10) REFERENCES products(product_id),
  quantity           INT NOT NULL CHECK (quantity > 0),
  unit_price_at_sale NUMERIC(10,2) NOT NULL, -- immutable snapshot
  PRIMARY KEY (order_id, product_id)
);

Why It Matters

If you referenced only products.list_price, raising a catalogue price would silently rewrite the financial history of every past order.

Multi-Node Distributed PostgreSQL (Citus Architecture)

        
Shard-Key Co-Location vs. Cross-Shard Fan-Out & Resharding

        

          

            
              

                Dimension
                Co-Located Pattern (tenant_id)
                Cross-Shard / Anti-Pattern Tradeoff
              

            
            
              

                Local Joins & FKs
                Both parent & child share distribution column; PK/UNIQUE include tenant_id; JOINs run locally on one worker.
                Mismatched shard keys force cross-worker data shuffling and network serialization overhead.
              

              

                Skew & Shard Count
                32–128 shards balance parallelism vs. planner metadata overhead (citus_rebalance_start()).
                A single "hot tenant" (whale customer) pins CPU/I/O onto one shard and worker node.
              

              

                Global Queries & Uniqueness
                Tenant-scoped queries route to 1 shard via the coordinator node.
                Global uniqueness, cross-shard transactions, and global Top-K (ORDER BY ... LIMIT K) require distributed coordination and merging top K per shard.
              

              

                Resharding & HA
                HA replicas on coordinator and workers eliminate single points of failure.
                Online resharding requires CDC replay, keyed checksum verification, and fencing stale writers; standalone nodes create SPOFs.
              

            
          

        

      

    


    
    

      

        
Section 03 · Execution Plans & Index Architecture

        
Decode EXPLAIN (ANALYZE, BUFFERS) bottom-up

        

          Never guess why a query is slow or whether an index helps. Click any plan node below to inspect inclusive timing, buffer hits vs. OS reads, loop multipliers, and row-estimate gaps.
        

      


      
      

        

          
          
        


        

          

          

        


        

          

            
Rule 1 · Inclusive Parents

            
Parent actual time and Buffers include all child nodes beneath them. Never sum the whole tree.

          

          

            
Rule 2 · Loops Multiply

            
Per-loop time × loops reveals hidden O(N×M) nested-loop or correlated SubPlan explosions.

          

          

            
Rule 3 · Statistics & Spill

            
Large est vs. actual row gaps need ANALYZE, SET STATISTICS 1000, or CREATE STATISTICS. external merge Disk signals work_mem spill.

          

          

            
Rule 4 · DML Safety

            
EXPLAIN ANALYZE executes UPDATE/DELETE! Wrap in BEGIN; ... ROLLBACK; (still takes locks & increments sequences).

          

        

      


      
      

        
Index Strategy & Sargability Explorer

        
Equality → Sort/Range Order, Leftmost Prefix & Specialized Indexes

        
Target schema: CREATE INDEX idx_orders_cust_created ON orders (customer_id, created_at DESC, id DESC) INCLUDE (total_amount);


        

          
          
        


        


        

          

            
              

                Index Type
                Best Workload
                PostgreSQL Syntax & Maintenance Note
              

            
            
              

                B-Tree (Default)
                Equality, ranges (< > BETWEEN), ORDER BY, prefix LIKE 'abc%' (with text_pattern_ops or C collation)
                Order composite keys: equality first, then range/sort. Build online with CREATE INDEX CONCURRENTLY.
              

              

                Covering (INCLUDE)
                Hot read queries answered via Index-Only Scan
                Depends on visibility map; stale VACUUM causes Heap Fetches.
              

              

                GIN
                JSONB containment, arrays, full-text search, pg_trgm %substr%
                Higher write cost than B-tree; prune unused indexes via pg_stat_user_indexes.
              

              

                BRIN & Hash
                BRIN: huge append-only time-series blocks; Hash: pure = lookups
                Rebuild bloated indexes safely via REINDEX CONCURRENTLY.

Section 05 · Materialized Views, Redis Caching & Self-Check

        
Freshness vs. speed & mastery verification

        

          Materialized views and Redis cache-aside both trade strict freshness for predictable latency. Compare their lock and invalidation failure modes, then test your recall.
        

      


      
      

        

          
            

              Dimension
              Live PostgreSQL Query
              PostgreSQL Materialized View
              Redis Cache-Aside
            

          
          
            

              Freshness
              Real-time (MVCC snapshot)
              Stale until next REFRESH
              TTL-bounded or event-invalidated
            

            

              Concurrency & Locks
              MVCC readers never block writers
              Non-concurrent refresh acquires exclusive locks on dependencies (can trigger OOM). Use CONCURRENTLY on high-dependency MVs.
              Must guard against cache stampedes and racing stale fills after invalidation; fall back to DB on RedisError.
            

            

              Hard Prerequisites
              Composite/covering indexes + pg_stat_statements
              CONCURRENTLY requires an already-populated MV + a UNIQUE index on plain columns; periodic REINDEX CONCURRENTLY.
              Namespaced/versioned keys (user:profile:{id}), bounded TTLs, allkeys-lru, appendonly yes.
            

            

              Best Pattern
              Transactional OLTP truth & low-latency seeks
              Dual-DB (Trans DB + Cache DB via FDW) or heavy multi-join reporting aggregates
              Hot entity reads & pre-warmed high-QPS lookups
            

          
        

      


      
      

        
Production Postmortem Patterns

        
Four High-Signal Failure Modes

        

          

            
01 · Silent Migration Corruption

            
Dropping legacy columns after coercing conflicts to NULL, or omitting default parent rows so existing insert paths fail FK checks.

          

          

            
02 · Benchmarking Without Baseline

            
Adding an index before capturing V1's EXPLAIN (ANALYZE, BUFFERS) conflates index impact with SQL rewrite impact.

          

          

            
03 · N+1 & Unbounded IN Lists

            
Fast 1 ms queries repeated 100× per HTTP call, or loading entire unpaginated child tables into JVM memory.

          

          

            
04 · Stale Cache Stamped as Fresh

            
Serving cached or materialized totals without surfacing their actual computation snapshot timestamp.
